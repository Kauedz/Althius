# Conta Unipile descartável durante a pré-produção

Enquanto a Althius não tem clientes, o backend usa uma única conta Unipile por vez, e essa conta troca pelo menos três vezes: o teste grátis de 7 dias do fundador, depois um plano pago numa conta pessoal de outro fundador, e por fim a conta oficial da empresa (Google Workspace pago), quando o produto escalar. Cada troca é uma conta Unipile diferente, não um upgrade da mesma conta.

A Unipile é só o meio de conexão ([ADR-0008](./0008-contas-remetentes-pessoais-e-interacoes-do-workspace.md)): o que ela entrega — chave de API e o segredo do webhook — já são segredos de ambiente das Edge Functions (`supabase/functions/README.md`), lidos a cada requisição. Trocar de conta Unipile é trocar esses dois valores (mais `APP_ORIGIN`, que não depende da Unipile) e recadastrar o webhook de conta na conta nova, apontando para a mesma URL da função (que não muda); nenhum código é publicado de novo. `docs/agents/migrations.md` descreve o procedimento como um todo, incluindo o wizard.

**2026-09-26 — conta nova veio em v2, não v1.** A conta Unipile criada pelo dashboard atual (`dashboardv2.unipile.com`) é v2-nativa: a documentação oficial da Unipile confirma que contas criadas em v2 não usam os endpoints v1 (sem retrocompatibilidade). O backend foi reescrito para os contratos v2 antes de qualquer conta real ser conectada, mantendo as mesmas garantias desta ADR: host único `api.unipile.com` (sem DSN por instância), hosted auth por `POST /v2/auth/link`, e um Webhook Endpoint único (`POST /v2/webhooks/endpoints`) que entrega todos os eventos `account.*` assinados por HMAC-SHA256 — a Unipile gera o segredo de assinatura, em vez da Althius escolhê-lo como na v1. A correlação da tentativa de conexão passou a usar o campo `state` (ecoado no evento `account.add`/`account.reconnect`) em vez do callback de redirecionamento dedicado que a v1 exigia. Nenhuma tabela ou garantia desta ADR mudou: a troca de conta continua sendo só os segredos das Edge Functions mais o recadastro do webhook.

O `unipile_account_id` de cada Conta remetente (`private.sender_accounts`) só existe dentro da conta Unipile onde a pessoa conectou. Numa troca, todas as Contas remetentes ficam órfãs: nenhum webhook chega mais para elas, então elas ficariam presas mostrando "pronta" sem estarem. A troca marca todas como `reconnect_required` (estado que já existe desde o canais-03), para a interface parar de mentir sobre a conexão. Ninguém tem seus dados apagados por isso: só a conexão precisa ser refeita.

Nenhuma outra tabela referencia `private.sender_accounts`. Contatos, Contas-alvo, Sequências e Interações (`public.contacts`, `public.target_accounts`, `private.sequence_documents`, `public.account_interactions`) são donos dos próprios dados e não dependem de qual conta Unipile está ativa; uma troca nunca os apaga nem os move. O canais-04 (primeiro ciclo real de E-mail) precisa manter essa garantia ao gravar o conteúdo das mensagens: a Interação grava o que aconteceu, não uma referência à mensagem na Unipile, porque a mensagem original desaparece da Unipile na próxima troca de conta.
